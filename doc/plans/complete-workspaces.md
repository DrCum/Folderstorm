# Complete workspaces

Status: planning only, review item **7**. Source baseline: unmerged PR1 at `65e6ebd115d7ef182e787a1541efb0305d95aa53`, inspected in `/workspace/Folderstorm`. This document is the only file this planning track writes. It does not modify PR1 or implement the feature.

## Result and first release

Add **Workspaces** under Preferences > Move & View. A workspace restores the current viewport/interface layout together with the positions, sizes, and visible/hidden state of a small set of utility windows. Users can save their current arrangement, preview another workspace, and cancel the preview. Provide **Inventory sorting** and **Driving** starting arrangements after the supported window adapters are complete.

Ship in two implementation stages: first the primary inventory window, maps, and compatible chat geometry; then one additional inventory window owned by the workspace feature. The second stage completes the useful two-window sorting workflow. More inventory windows and additional panels require separate allowlist entries and acceptance checks; a generic “save every floater” system is outside this plan.

Keep interface layout profiles working as they do in PR1. Workspaces get an account-local collection with a versioned envelope containing the existing chrome snapshot. The new Workspaces panel explains its coverage: “Saves viewport, bars, utility windows, and supported panel sizes. Conversations and inventory contents stay as they are.” Existing layout profiles can be used to establish a layout and then saved as a workspace; no automatic conversion or destructive migration is needed.

## Source facts that constrain the design

| Touchpoint | Current behavior and implication |
| --- | --- |
| `fschromelayout.h`, `Snapshot`; `FSChromeLayoutController::captureSnapshot()/applySnapshot()/snapshotToLLSD()/snapshotFromLLSD()` | Schema 1 stores viewport insets and interface-bar placement. It has no floater or panel state; `FSWorldViewInMouselook` is not in the snapshot. Use the snapshot as a nested component rather than extending the existing permissive deserializer. |
| `app_settings/settings.xml`, `FSChromeLayoutProfiles`, `FSChromeActiveProfile` | Layout profiles are global viewer settings. New account-specific windows/panels must not silently enter that global collection. |
| `LLFloater::getControlGroup()/storeRectControl()/storeVisibilityControl()/applyRectControl()` in `llui/llfloater.cpp` | Ordinary window settings are per-account. Hosted floaters deliberately do not store visible state; rectangle persistence can use both rectangle and relative-position controls. A bare `setRect()` does not update all placement/persistence state. |
| `LLFloaterReg::findInstance()/getInstance()/showInstance()/hideInstance()` in `llui/llfloaterreg.cpp` | `findInstance` is side-effect free; `getInstance` can build and position a window. `showInstance` invokes `openFloater`, which reapplies controls and calls `onOpen`. `hideInstance` calls `closeHostedFloater`, which can close a host. Capture must use find, and hosted windows need explicit adapters. |
| `LLViewerFloaterReg::registerFloaters()` in `llviewerfloaterreg.cpp` | Actual registry names include `inventory`, `secondary_inventory`, `fs_nearby_chat`, `fs_im_container`, `mini_map`, and `world_map`. Do not identify windows by translated titles or XUI display names. |
| `LLPanelMainInventory::newWindow()`; `LLSidepanelInventory::createSecondaryInventoryWindow()`; `LLFloaterSidePanelContainer::closeFloater()` | Extra Inventory windows may use numeric keys under `inventory`; the secondary builder constructs with `is_secondary=true` and discards its caller key. Keyed Inventory/secondary windows are destroyed on close. Replaying arbitrary keys or treating all Inventory windows as a singleton is unsafe. |
| `FSFloaterNearbyChat::onOpen()/isChatMultiTab()`; `FSFloaterIMContainer::initTabs()/addFloater()/removeFloater()` | Nearby chat can be standalone or hosted in the conversations container. Opening a host can initialize other tabs. Chat mode is statically cached in `isChatMultiTab()`. Workspaces must preserve the current presentation and must not change `FSChatWindow` or serialize/reconstruct IM sessions. |
| `LLSidepanelInventory::postBuild()/toggleInbox()/~LLSidepanelInventory()`; `sidepanel_inventory.xml` | The primary Received Items panel uses `InventoryInboxToggleState`, `InventoryInboxHeight`, `inventory_layout_stack` and `inbox_layout_panel`. Secondary windows intentionally handle Inbox differently. This is the first supported inner-panel layout, not a license to serialize child controls. |
| `LLFloaterView::adjustToFitScreen()`; `FSChromeLayoutController::applyFloaterSnapView()` | Existing fit logic handles minimum sizes and reserved toolbars, and PR1 permits floaters in utility gutters. Use full floater/client space for workspace coordinates, not only the 3D world rectangle. |
| `LLFloaterPreference::saveViewportSettings()/cancelViewportSettings()` in PR1 | Preferences already snapshots layout settings and the profile map, with revisions guarding delayed overwrite/delete prompts. Extend the transaction to workspaces and managed runtime windows instead of starting an unrelated preview mechanism. |
| `LLStartUp::setStartupState()/postStartupState()`, `llstartup.cpp`; `LLAppViewer::addOnIdleCallback()` | Initial visible windows are restored before `STATE_STARTED`. There is a `StartupState` event stream and a one-shot idle callback. Applying windows too early lets normal login initialization overwrite the workspace. |

## Safe adapter allowlist

Capture only these roles. Each role has a compiled adapter, a declared presentation contract, and bounded fields. The deserializer never turns a stored string into an arbitrary `LLFloaterReg::getInstance()` call.

| Role | Stage | Fields and restore behavior |
| --- | --- | --- |
| `inventory_primary` | 1 | Registry `inventory` with undefined key only. Capture normal rectangle, visible/minimized state, and supported primary Inbox split/collapse state. Restore by ordinary primary Inventory lifecycle; hide only this unkeyed window. |
| `mini_map` | 1 | Registry `mini_map`, no key. Capture rectangle, visibility and minimized state. Do not save map center, zoom, tracked avatars, parcel state, or location. |
| `world_map` | 1 | Registry `world_map`, no key. Capture rectangle, visibility and minimized state. Do not save searches, map coordinates, selections, routes, landmarks, or teleport targets. |
| `nearby_chat` | 1 | Registry `fs_nearby_chat`, standalone only (`getHost()==nullptr` and parent is `gFloaterView`). Capture rectangle and visibility. Preserve current `ChatHistoryTornOff`/chat-mode settings; if hosted at apply time, skip this role with a clear explanation instead of tearing it off or hiding the host. |
| `conversations_geometry` | 1 | Registry `fs_im_container`, **existing instance only**. Capture/restore normal host rectangle, when present. Never create, show, hide, minimize, select tabs, close sessions, or alter tab order through this role. Missing instance is a reported skip. This preserves hosted chat positioning without importing session state. |
| `inventory_extra_1` | 2 | One dedicated workspace-owned inventory window, with normal rectangle, visibility/minimized state, and no inventory selection/filter/content. Build using the existing secondary-inventory semantics with a distinct registration/group and lifetime adapter; see below. |

Missing/never-created allowed windows are saved as `visible:false`, with no invented geometry. Existing hidden standalone utility windows may retain their normal rectangle in the record, but `visible:false` must never create or open them during restore. A minimized floater is captured using its expanded/normal rectangle, never the minimized icon's rectangle. Restore size before restoring minimize state.

Exclude all unknown floaters and arbitrary keys: IM sessions, contacts/profile/avatar inspectors, item properties, script/notecard/texture editors, offers/notifications, file pickers, login/security/preferences dialogs, appearance editors with unsaved work, camera-control floaters, permission prompts, and dependent/hosted tabs not listed above. Do not store avatar UUIDs, inventory folder/item UUIDs, selected folder, filters/search strings, conversation names/transcripts/drafts, session keys, map destinations, file paths, credentials, or device/display identifiers. User-authored workspace names are retained as plain local labels. Workspaces store local arrangement, not actions such as wearing items, moving inventory, joining chats, driving, or teleporting.

For panels, stage 1 supports only the primary Inbox expanded/collapsed flag and target height. Add narrow `LLSidepanelInventory` capture/apply methods that use the existing layout stack and collapse logic without changing whether Inbox exists or is enabled. Clamp height against the current inventory window and the panels' minimum dimensions. When Inbox is unavailable, retain the saved preference and report that its panel adjustment was skipped; do not enable/fetch it solely to satisfy a workspace. Gallery/list splits and arbitrary panel-state serialization are deferred until separately specified.

## Data format and compatibility

Add `FSWorkspaceProfiles` (LLSD map) and `FSActiveWorkspace` (string) to `settings_per_account.xml`. Use the same existing safe-name validation rules for names, with a bounded maximum of 32 saved workspaces. Keep builtin template IDs reserved and read-only. Initial workspace schema is **1**, separate from the existing chrome snapshot schema **1**:

```text
FSWorkspaceProfiles[name] = {
  schema: 1,
  type: "workspace",
  chrome: <existing FSChromeLayoutController schema-1 snapshot>,
  world_view_in_mouselook: <bool>,
  frame: { width_ui: <positive number>, height_ui: <positive number> },
  windows: {
    inventory_primary: { visible: true, minimized: false,
      center_x: 0.82, center_y: 0.52, width_ui: 333, height_ui: 570 },
    mini_map: { visible: false }
  },
  panels: { inventory_primary_inbox: { expanded: false, height_ui: 200 } }
}
```

Centers are normalized to the saved full `gFloaterView` client frame, with bottom-left origin. Width/height are UI-scaled logical units; the frame dimensions describe the capture environment for diagnostics and validation, not an instruction to resize the OS window. Optional records are absent when a role is unsupported in that presentation. Host-geometry records omit visibility/minimized fields entirely.

Schema handling is strict and side-effect free before application: validate the envelope, recognized type/version, nested chrome schema, allowlisted role keys, finite coordinates/dimensions and bounded record count. Clamp reasonable out-of-range positions at placement time; reject non-finite, negative/zero size or wildly oversized records. Bound logical sizes to 16,384 units and enforce at most the six defined roles. Unknown role/field extensions can be ignored with an unsupported-details count; a future top-level schema is listed as unsupported and cannot be applied or overwritten accidentally. A missing required envelope field or malformed chrome snapshot fails application without touching current settings. Do not default malformed data to a standard layout.

Existing global schema-1 layout profiles remain untouched and remain available in their existing panel. **Save current workspace** captures their effective current layout into the new envelope; it does not delete, rewrite, or rename the original. A later workspace schema migration must be an explicit pure transform applied to a copy, with the original retained until a valid new save succeeds. No account names/UUIDs are embedded in profile records; storage scope supplies account separation. Export/import and cross-account synchronization are deferred.

## Placement, DPI, monitor removal and tiny windows

Workspaces reuse PR1's percentage viewport and chrome behavior. Apply that component first, then obtain the current full floater frame after the controller has settled. Do not refit the viewport to a physical monitor, save the PR1 monitor selection, resize/span the OS window, or make a workspace follow displays automatically.

For each standalone role, restore its normalized center in the current full frame and preserve its saved size in UI logical units. This keeps controls readable when DPI/Retina or UI scale changes and moves off-monitor positions into the resized client after unplugging a display. Convert to the current parent view once; do not mix raw drawable pixels, desktop coordinates and UI-scaled rectangles. For unchanged frame/scale, capture/apply must round-trip within one UI unit.

Respect the floater's actual skin/runtime minimum sizes (`getResizeLimits()`), rather than hard-coded XUI dimensions. Clamp requested dimensions to the current frame when the floater's minimum permits it, then use `gFloaterView->adjustToFitScreen(floater, false)` to keep it reachable and respect reserved chrome. If a minimum is larger than the client frame, retain the minimum, put the close/title controls inside the client at the top, and report “Some windows were adjusted to fit.” Do not shrink below minima or repeatedly retry. Overlap is allowed on tiny windows; apply bounded small offsets to overlapping restored top edges so one window does not trap another's controls. For headerless Mini-map, keep its caption/menu affordance reachable. Native-monitor availability is unnecessary for workspace placement, so Wayland/headless fallback does not block the geometry math.

Introduce a narrow public `LLFloater` workspace geometry interface if necessary: a read-only normal-rectangle accessor and an apply method that updates shape, relative-position state, expanded rectangle, and the usual account rect/position controls. Reuse protected `storeRectControl()` internally. Do not call only `setRect()` or mutate private members from newview. This hook must not change dock/host state or globally change ordinary floater positioning. Its tiny-window behavior gets a focused test/manual check with current skins.

Account for the primary Inventory group specifically: `applyRectControl()` can switch to cascading placement and clear a rectangle control when other Inventory instances exist. The primary adapter must still preserve/reapply its supported unkeyed placement on reopen without rewriting a manual extra's live geometry. Add a narrowly scoped primary-role persistence path through the floater interface where needed; do not change group cascading for ordinary windows. Primary Inventory edits may update its ordinary shared default size as they already do; the dedicated extra must use independent controls.

## Apply, login, preview and persistence

MVP is **manual restore after login**. Saving and applying workspace windows are disabled until `STATE_STARTED`, the account settings are loaded, `gFloaterView` exists, and the controller is ready. Pre-login UI can explain “Workspaces are available after login”; it does not queue an application to whichever account logs in next. Geometry does not need the entire inventory tree fetched: panels can open and fill normally while content loads.

One workspace apply is a scoped, generation-tagged UI operation:

1. Validate the complete envelope and produce the allowlisted plan with proposed adjustments/skips. Nothing is changed on failure.
2. Capture the Preferences preview baseline if not already captured for this session: PR1 layout/settings/profile state, workspace collection/active ID, the managed runtime roles and relevant per-account window controls/panel state. Keep runtime `LLHandle` identities separately from saved profile data.
3. Apply the chrome snapshot and Mouselook flag. Set the active workspace ID only after application has been accepted; clear `FSChromeActiveProfile` for a full workspace apply so the UI does not suggest an unrelated layout profile still matches. Both active IDs participate in Cancel.
4. Use `findInstance()` for all hidden/existing-only roles. For supported roles intended visible, call the appropriate ordinary show adapter once, honoring `canShowInstance()` and current restrictions; never bypass viewer visibility validation. Host chat geometry uses only an existing host. Avoid `hideInstance()` on a hosted child.
5. Schedule one bounded idle continuation with `LLAppViewer::addOnIdleCallback()` after normal `onOpen()` placement/panel construction. Re-check operation generation, account/session identity, `STATE_STARTED`, live handles, and presentation compatibility. Then apply geometry, supported panel sizes, visibility/minimize state and owned-window ordering. Do not retain raw pointers or repeatedly call `showInstance()` on each frame. Restore the user's prior focus where its handle survives; workspace previews do not select a conversation or move focus out of Preferences.
6. Report applied/adjusted/skipped role counts in the Workspaces panel. Partial adapter failures retain successfully previewed roles and remain reversible with Cancel; the saved definition is not silently rewritten to fitted geometry. A profile requiring a hosted/standalone chat conversion is skipped with a specific reason.

New Apply, Cancel, close, logout, account change or shutdown invalidates older continuations before they can open/move a window. A delayed role construction may finish without the feature acting on it; cancellation then hides only feature-created utility instances where necessary. The existing chat/account session state is never reset as rollback.

The Nearby Chat adapter must preflight the current presentation settings even when no instance exists: its ordinary `onOpen()` can build a host and attach itself according to `ChatHistoryTornOff`. Do not show a saved standalone role when current settings would host it; report a presentation mismatch before creating/showing it. Recheck the actual host after opening and before placement. A workspace cannot use a generic show path to introduce a chat host or tear-off conversion as an incidental side effect.

**Save current**, overwrite, rename and delete participate in the same Preferences transaction as PR1's layout profile controls. Explicit OK acceptance refreshes the baseline and retains the preview; Preferences Cancel/close restores baseline geometry, visibility/minimize/panel state and the workspace map/active ID. Delayed overwrite/delete confirmations carry the transaction revision and cannot mutate the next session. Extend PR1's scoped methods or delegate both to one layout/workspace transaction owner; avoid separate cancellation ordering that overwrites the freshly restored viewport. The current Preferences UI has OK and Cancel; generic `apply()` is also invoked from `postBuild()`, and `saveSettings()` captures baselines on opening. Neither is an acceptance event. Coordinate with item 5's explicit acceptance hook in `onBtnOK()` before baseline capture. An explicit Apply button, if added later, must call that same acceptance hook; merely constructing or reopening the panel must never commit a pending workspace transaction.

Rollback covers only allowed roles actually touched by the preview and feature-owned creations. Restore per-account rectangle/relative-position/visibility controls as well as live window shapes, or reopening later could resurrect the preview placement. Leave IM sessions, incoming conversations and manually created unrelated floaters alone. If a tracked instance was destroyed, use its allowlisted role adapter when baseline visibility requires restoration; never replay its old arbitrary key. An unowned extra Inventory window created after the baseline remains unowned. Explicit acceptance commits a new baseline even if some roles were skipped; keep the skip report visible.

Do not continuously rewrite named workspaces on window movement or logout. Moving windows/layout after applying a workspace displays **Modified** based on a bounded comparison of supported fields. It does not overwrite the saved workspace or immediately snap the user back. Ordinary existing per-account window persistence continues normally. Reapplying restores the saved definition, not the most recent incidental geometry.

Optional **Restore this workspace after login** is a later phase, default off. It must wait for `StartupState`=`STATE_STARTED` and the following idle frame after `showInitialVisibleInstances()`, use the committed account-local ID, and apply once per successful login/session generation. Failure is a reported one-shot partial result, not a retry loop. Turning it off leaves normal login visibility restoration intact. A cancelled Preferences preview must never become the startup choice.

## Extra inventory ownership (stage 2)

Use one dedicated role `inventory_extra_1`, not a stored existing instance number, item UUID or folder UUID. Add a distinct registration/group such as `fs_workspace_inventory` with a small inventory-container adapter that preserves the existing `is_secondary=true` construction semantics and has an explicit close/destroy lifecycle. A distinct group avoids `LLFloater::applyRectControl()` cascading against manual `inventory` instances or clearing their shared rectangle control. Do not use the current secondary builder's ignored key as a slot identity.

Expose **Add workspace inventory window** in the Workspaces panel and let the Inventory sorting template request this role. Saving captures this owned window only; manually opened additional Inventory windows are not automatically adopted, renamed, closed or counted as the owned role. There is at most one owned extra instance per account session, reused across workspace previews to prevent leaks. Its visibility=false action closes/hides this owned window according to its adapter, never all extra Inventory windows. Cancel destroys a newly created owned extra or recreates the single baseline role when it was closed; invalidate old handles before reuse. Inventory contents/selections and Inbox eligibility remain controlled by the existing inventory implementation. Additional numbered slots require a separate bounded schema extension and lifecycle tests.

## Starting arrangements and UI

Keep builtin starting arrangements separate from saved immutable snapshot records. Generate them against the current full UI frame, preserve the user's current viewport/chrome/Mouselook component, and send them through the same validation/apply transaction. No assumptions about equal monitor widths are embedded.

- **Inventory sorting:** primary Inventory in a usable right utility gutter when available; otherwise use the right side of the full floater frame. In stage 2 place the workspace-owned extra beside it, using left utility space when available. Make both visible and non-minimized. Hide only the allowlisted standalone maps; leave existing chat host visibility unchanged. On a small frame, fit readable minimum sizes and permit staggered overlap. Save the arrangement under a custom name after user adjustment. Do not preselect folders/items or alter sorting/filter preferences.
- **Driving:** show a roughly 220×220 UI-unit Mini-map near the upper-left usable edge; hide primary and workspace-owned extra Inventory and World Map. Preserve chat presentation and existing chat host visibility; position a currently standalone Nearby Chat near the lower utility edge without changing transcripts or input. Do not change the camera, avatar, vehicle controls, draw distance, permissions or keyboard bindings.

The panel has a workspace selector, **Preview**, **Save current**, **Rename**, **Delete**, a name field, the two starting-arrangement buttons, and a short coverage/adjustments status. Only custom saved workspaces can be renamed/deleted. Overwrite/delete reuse scoped, revision-guarded confirmations. Preferences OK/Cancel provide the commit/revert behavior; any future explicit Apply button follows the same acceptance contract. Add localized strings and Preferences search keywords; account-unavailable/unsupported-schema/skipped-chat explanations must fit at minimum Preferences size and larger UI scales.

## Implementation stages, owners and dependency strategy

1. **Data/geometry contract:** add pure workspace records, strict LLSD serialization/validation and fitting helpers (proposed `fsworkspacelayout.{h,cpp}`), account settings, and tests. Fix role IDs and normalized/UI-unit contract before runtime/UI agents start. Own the generic `LLFloater` geometry hook in this stage; do not spread private geometry writes across adapters.
2. **Runtime MVP:** a focused `FSWorkspaceController` owns allowlist adapters, operation generations, per-account lookup, capture/apply results and scoped live rollback. Implement primary Inventory/maps, current-presentation Nearby Chat and existing-host geometry, plus the Inbox adapter. Main-thread UI only; no new network actions or render loop polling beyond modified-state observation.
3. **Preferences integration:** a dedicated workspace panel owns UI controls. One integration owner connects PR1's save/cancel lifecycle, active IDs and revision-protected dialogs, with asynchronous apply cancellation before baseline restoration. Leave the assistant preferences panel and permission changes untouched. Data/geometry tests and XUI/static checks may proceed in parallel with runtime adapters once the contract is fixed.
4. **One owned extra Inventory and templates:** land the dedicated registration/lifetime adapter and two starting arrangements. This phase touches inventory factory/registration paths, so assign it one owner. Test it with manual additional windows and repeated preview/cancel before declaring the two-window sorting workflow complete.
5. **GUI acceptance and optional startup restore:** complete native/window/skin/scale checks for the manual feature. Add opt-in restore-after-login in a separate follow-up change only after the transaction/lifecycle tests pass.

## Acceptance and failure checks

- Pure tests cover valid capture/round-trip, malformed/non-finite/oversized fields, unknown roles, missing nested fields, unsupported future schema, profile name/count limits and untouched existing layout profiles. Unsupported data must fail before any runtime/settings mutation.
- Placement fixtures cover non-zero frame origin, narrow/small windows, unequal multi-monitor spanning, saved centers outside the new client, changed UI scale/DPI, minimum-size conflicts, and capture/apply within one UI unit. Native GUI checks confirm readable controls and accessible close/menu affordances after monitor removal.
- Capture reads no new instances. `visible:false` never creates a window. Applying primary Inventory does not create numeric-key windows or move/hide manual extras. Unsupported/unregistered roles are never instantiated from serialized strings.
- Standalone chat restores geometry/visibility; hosted chat is skipped or uses existing-host geometry without changing host visibility, selected tabs, session count, input drafts, contacts or `FSChatWindow`/tear-off settings. No hide path accidentally calls `closeHostedFloater()` on the child.
- Inbox collapse/height restores only where enabled and respects current pane minima; saving/restoring with unloaded inventory or an absent Inbox does not enable content or fetch additional folders.
- Repeated A→B preview, Cancel, close, explicit OK (and any future explicit Apply), reopen, save/overwrite/rename/delete and late confirmation callbacks restore/commit both live geometry and ordinary per-account position controls. Reopening a hidden utility window after Cancel uses the baseline position.
- Account change/logout/shutdown between opening and idle placement cancels old work. The late continuation cannot open a window for another account. Missing/destroyed handles produce bounded skips; no raw pointer use or repeated-creation loop.
- An incoming IM during preview remains intact through Cancel. Unowned windows opened after baseline remain intact. Workspace state contains no conversations, item/folder UUIDs, typed text, map destinations or arbitrary registry keys.
- Stage 2 repeats create/hide/destroy/preview/cancel with the owned extra and multiple manual extra windows; registry counts show no leaks or duplicates, baseline recreation is deterministic, and owned-extra actions do not change shared manual geometry controls. Primary Inventory persistence remains correct when group cascading is active.
- Inventory sorting and Driving operate on unequal/tiny layouts, supported skins and high UI scales; they preserve the current viewport/chrome component and make no camera, inventory-content or session changes. Skips/adjustments are visible and the named saved definition remains unchanged.
- Existing PR1 viewport/profile and assistant tests still pass. Building each supported viewer backend plus GUI/manual acceptance is required for implementation; no native viewer or workspace tests were run for this planning-only document.
