# Release checking and publishing checkpoint

Build identity and native widgets are shared with existing Folderstorm code.
No installer is downloaded or run automatically in this checkpoint. It works
with NSIS; Velopack is a later checkpoint.

## Build and feed configuration

The default feed is the public `DrCum/Folderstorm` GitHub releases API, with at
most 32 entries. Only non-draft releases carrying the publisher's versioned
metadata block are considered. Nightly uses GitHub prereleases; Stable excludes
them. Numeric comparison includes the full build component. Installer selection
requires the same platform, architecture, CPU level, grid flavor and installer
type. GitHub downloads must also exist in that release's uploaded asset catalog
with the declared size. No suitable artifact leaves Download unavailable and
offers the release page instead.

For static hosting configure `FS_RELEASE_FEED_URL` to the exact HTTPS manifest
URL and `FS_RELEASE_DOWNLOAD_HOSTS` to a comma-separated hostname allowlist.
GitHub links are confined to this repository's releases. No credentials belong
in either value. Use `folderstorm-releases.json` generated by the publisher.
The static feed uses schema 1 with a bounded `releases` array; each release has
version/channel/commit/url/notes and exact typed assets with byte counts/SHA256.

The host and viewer share persistent update choices outside installation/private
profile folders. Windows stores these in
`%LOCALAPPDATA%/FolderstormSessions/Updates-v1/preferences.dat`. Other platforms
use the user's XDG config directory (or `~/.config/folderstorm/updates-v1`).
Fresh builds use their matching Stable/Nightly channel and automatic checks
every 12 hours. Manual checks bypass this timer and skipped-version suppression.
Managed workers skip automatic checks; the host checks once. Preferences Cancel
discards choice edits. Starting an actual check records its time independently.

## Preparing retained build artifacts

Create a JSON input with the exact version, commit, notes and variants:

```json
{
  "version": "7.2.5.82125",
  "channel": "nightly",
  "commit": "0123456789abcdef0123456789abcdef01234567",
  "notes_file": "changes.md",
  "assets": [{
    "file": "Folderstorm-Setup.exe",
    "platform": "windows", "architecture": "x86_64", "cpu": "avx2",
    "flavor": "opensim", "installer": "nsis"
  }]
}
```

```sh
python3 scripts/folderstorm_release.py release-input.json --output prepared
```

This hashes the retained files and writes a release manifest, cumulative static
feed and changelog with GitHub metadata. Use `--previous-feed` to retain earlier
versions/channels. `--download-base https://your-host.example/downloads` generates
links for existing HTTPS hosting; add its hostname to the build allowlist.
Publishing a changed build requires a new version: conflicting existing release
identities are rejected. The tool validates declared variants and hashes files;
the maintainer must verify those declarations describe the actual retained build.

`--github-draft` explicitly creates a draft and uploads retained installers using
the maintainer's `gh` authentication. It never builds or publishes a release.
A failed upload leaves a draft. Verify every upload and the exact source/build
before publishing; deploy a static feed only after its assets are available.
GitHub assets must each be under 2 GiB; use external hosting for larger files.

## Focused checks and limits

Five publisher tests and the strict C++17 release-policy test cover numeric
ordering/overflow, channels/skips, missing/duplicate downloads, URL boundaries,
settings encode/decode, checksums, input limits and immutable publishing IDs.
Changed XUI parses as XML. The existing Windows host tests and native build still
need acceptance; portable checks do not exercise WinHTTP, native dialogs or GPU.
No actual release, installer build, live upload or hosting deployment was made.
The GitHub feed is empty until a maintainer publishes a prepared release.

## Native acceptance

1. In standalone viewer Help, Check for updates opens the Folderstorm window,
   displays checking/result text, and keeps UI responsive. An empty repository
   reports no published releases; network/rate-limit failure offers All releases.
2. Host Preferences → Updates and the title-bar system menu offer the same check.
   Check with five managed workers: only the host performs an automatic check.
3. Publish a disposable prepared test release using real retained test installers.
   Verify current/new version, plain-text notes, explicit Download and What's new,
   Skip and Later. Stable excludes the nightly prerelease. Wrong CPU, flavor,
   installer or missing uploads must never produce an executable download button.
4. Apply/Cancel update choices, restart and upgrade installs; check they persist
   independently of private profiles. Manual checks can show a skipped version.
5. Test DPI, screen readers and the host's detached/monitor system menus. Close
   during a check: no completion touches a destroyed HWND. Host shutdown may wait
   for its bounded in-flight network worker, and no viewer is logged out.
